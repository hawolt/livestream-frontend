# Architecture

How each page in this repo works, based on the code in `src/` and `public/`. Every page is an independent Bun bundle loaded by its own HTML file; there is no router and no shared framework, only a handful of shared modules.

All API descriptions in this document are from the client's perspective: the request this code sends and the response fields this code reads.

## Shared runtime

### `src/api.ts`

- `API_BASE = "/api/main/v1"`. `apiFetch(path, init)` rewrites a leading `/api/` in the path to `API_BASE`, sends JSON, and throws an `Error` with a `.status` field on non-2xx responses (reading `{error}` from the body when present). `204` and empty bodies resolve to `undefined`.
- Declares the response shapes the dashboard consumes: `AccountSettings`, `LiveInfo`, `LiveCategory`, `LiveBan`, `LiveMod`, `RegionOption`.

### `src/dash/` (dashboard runtime)

- `session.ts`: the session token lives in `sessionStorage` under `dash_token` (`token()` / `setToken()`), the session kind under `dash_kind`. `bootstrapSessionFromCookie()` calls `GET /api/auth/session` and, if it returns `{token, kind}`, stores both. This is how a session established elsewhere on the site (via the session cookie) is picked up without a login form. `authFetch()` wraps `apiFetch` with a `Bearer` header; a 401 or 403 triggers `loginRedirect()`/`signOutAndRedirect()` (best-effort `POST /api/auth/logout`, clear storage, `location.replace("/login")`). Also holds `MeInfo`/`TabInfo`/`TabModule` and `loadDashboardSession()`.
- `regions.ts`: `loadRegions()` fetches `GET /api/regions` once and caches the `{regions: [{id, label}]}` list for the session.
- `modal.ts`: `openModal`/`closeModal` with focus trap and focus restore.
- `format.ts`: `esc()` HTML escaping, secret masking, copy/reveal button wiring, and date/uptime formatters.
- `dom.ts`: the `$`/`$$` element lookup helpers shared across the dashboard shell and tab modules.
- `tabs/`: one module per dashboard tab, described under Dashboard below.

### `src/nav.ts` (site navbar)

`initSiteNav(active, pageControls?)` runs on every page with a navbar:

- Marks the active nav item (`markActive`), inserts the kebab menu (Pricing `/pricing`, Guides `/guides`, API `/docs`, Status, Terms `/terms`, Privacy `/privacy`, Impressum `/impressum`), and appends Discord/GitHub icon links. The site has no footer, so this menu is the only sitewide internal link surface a new page can join.
- Fetches `GET /api/auth/session` with credentials. A `kind === "user"` session renders the gear account menu (username, Dashboard link, Sign out); otherwise Login and Sign up links carrying `?return=<current URL>`.
- Sign out (`signOut`, shared by the account menu and the hamburger menu) posts `/api/auth/logout` with the session token, clears `dash_token`/`dash_kind`, and reloads.
- Builds a hamburger menu that mirrors the page's own control buttons (`pageControls`): it clones each visible `HTMLButtonElement` as a menu item that forwards the click and rebuilds itself, so labels stay current. `setBurgerExtra()` lets a page (the dashboard) prepend its own items.

`initSiteNav` and `markActive` stay exported from `nav.ts` itself, which also keeps the kebab menu, the social links, and session renewal. The account gear menu and the hamburger menu live in `src/nav/`: `account-menu.ts` (`buildSignedIn`/`buildSignedOut`), `burger.ts` (`buildBurger`, `setBurgerExtra` and its provider state), and `dropdown.ts` (the shared open/close/outside-click/Escape wiring both menus use).

### `src/storage.ts`

`readLocalStorage` / `writeLocalStorage` / `removeLocalStorage`: localStorage wrappers that swallow exceptions (private browsing, blocked storage).

### `src/captcha.ts` (viewer token mint)

Used only by the viewer and embed player. No challenge widget: the owner removed the Turnstile challenge from the playback token flow on 2026-08-13 (BunnyCDN migration), since WS+MSE stopped being the default viewer path and became the paid `watch_ll` low-latency perk instead, so a viewer without a token simply plays HLS at claim 0 rather than being blocked. `getCaptchaToken()`:

1. Fetches `GET /api/live/captcha/config` once; `{enabled}` (the response still carries `challenge`/`sitekey` for wire compatibility; both are ignored). Disabled means every call resolves to `""` and nothing else happens.
2. Posts an empty body to `POST /api/live/captcha/token`, caching the returned `{token, ttl}` until 60 s before expiry. Failures resolve to `""` (fail-open on the client).

`captchaQuery()` returns `"&t=<token>"` for splicing onto media URLs; `freshCaptchaQuery()` mints uncached (used by the raid prewarm, since the per-nonce use cap forbids reusing the player's token); `warmCaptcha()` pre-mints in the background. The raw token from `getCaptchaToken()` also feeds `src/player-shared/viewer-claim.ts` (`parseViewerClaim`) for transport selection, see "Transport selection" under the channel viewer below.

## Explorer (`src/explore.ts`)

State is `mode` (`"streams" | "categories"`) plus an optional category selector, driven entirely by the URL (`/?category=<id>`, `/?category=none` for uncategorized, anything else renders a not-found view). Mode switches and category drill-downs `pushState`; `popstate` restores state, so back/forward work.

- **Loading**: `GET /api/live/explore` once on boot. The response provides `streams` (`username`, `title`, `category`, `categoryId`, `viewers`, optional per-stream `mediaBase`), `categories` (`id`, `name`, `liveStreamCount`, `viewerCount`), and a default `mediaBase`.
- **Stream cards** are cached per username and updated in place (title, category tag, viewer count); a card leaving the live set is dropped from the cache. Cards are sorted by viewers.
- **Thumbnails** load from `<mediaBase>/thumb/<username>.jpg?t=<minute>`: the URL only changes once per minute, and `img.src` is only reassigned when the computed URL differs, so thumbnails do not flicker on re-render. Broken images hide themselves.
- **Hover live preview**: on devices matching `(any-hover: hover) and (any-pointer: fine) and (prefers-reduced-motion: no-preference)`, hovering a card's thumbnail for 300 ms overlays an iframe of `/embed/<username>?preview=1`. The embed reports its state back via `postMessage` (`itzon:stream-preview`, states `connecting`/`playing`/`unavailable`), which drives the card's status chip. Grid re-renders are deferred while a preview is active and applied when it ends; previews stop on pointer leave, page hide, or tab visibility loss.
- **Category mode** renders category cards (plus a synthetic "No category" card when uncategorized streams exist), sorted by summed viewers; clicking one drills into its stream list.
- **Framed mode**: when the page detects it is inside an iframe (or `?framed=1`), it skips the navbar, adds `explore-framed`, and stream card links get `target="_top"`. This is what the viewer's browse mode embeds.

- **Language filter**: a typeahead input (`src/typeahead.ts`, the shared combobox: substring filtering over labels via the pure `filterTypeaheadOptions`, keyboard navigation, exact-label commit on blur, revert otherwise) sits right of the Streams/Categories mode buttons. Picking a language sets `ctx.languageFilter` and filters every stream list, both the Streams mode grid and a category drill-down (`src/explore/language-filter.ts`, pure, tested: a stream matches when any of its up-to-two codes equals the selected one; `und` streams never match a concrete filter). The category card grid is unaffected, "Any language" clears it, and the filter is session-only, never in the URL. The same typeahead component powers the dashboard's stream info Category/Language/Second language fields.

`explore.ts` is the entry: it wires the mode/back buttons, the language filter, the grid's category click delegation, `popstate`, and boot. The rest lives in `src/explore/`: `context.ts` (shared state and types, `isFramed`), `dom.ts` (element lookups), `thumb-url.ts` (the pure minute-bucketed thumbnail URL builder), `stream-cards.ts` (card cache, grid rendering), `preview.ts` (the hover preview overlay and its `postMessage` handling), `categories.ts` (category grid and drill-down), `url-state.ts` (pure URL/`ViewState` conversion), `render.ts` (mode dispatch and `pushState` navigation), `seo.ts` (the per-route title/description/canonical/heading, see the SEO surface section), and `poll.ts` (the `GET /api/live/explore` load).

- **Per-route SEO**: `/`, `/categories` and `/category/<name>` are the same HTML shell, so a static canonical would collapse all three onto the homepage. `render()` calls `applyExploreSeo(exploreSeo(mode, drilledCategoryName()))` on every state change (skipped in framed mode), which rewrites `document.title`, the description, the `og:`/`twitter:` title and description, `og:url`, the `<link rel="canonical">` and the visually hidden `<h1 id="explore-heading">`. `exploreSeo` is pure and tested; a category that fails to resolve canonicalizes back to `/categories` rather than pointing at a URL that renders a not-found view.

## Ads (`src/ads.ts`)

Used only by the channel viewer's chat-column spot. `loadAds(slot)` fetches `GET /api/live/spots?slot=<slot>` as a plain `fetch` (no `apiFetch` rewrite, since `/api/live/` passes straight through Apache), attaching a `Bearer` header from the `dash_token` in `sessionStorage` when it decodes as a valid session (`session-token.ts`). Any non-OK response, thrown error, or non-array `ads` field resolves to an empty list. `renderAdSlot(container, ads)` clears the container and, for a non-empty list, builds one class-less, id-less `<a href="/api/live/spots/visit/<id>" target="_blank" rel="noopener noreferrer nofollow sponsored">` containing an `<img>` (carrying the ad's alt text) and a plain `<span>` reading "Anzeige", entirely with `document.createElement` and inline styles; only the first ad in the response is rendered, and an empty list renders nothing. Visiting the link itself counts the visit and redirects server-side, so the anchor needs no click handler.

## Channel viewer (`src/live.ts`)

Boot first checks the path against the clip route `^/([a-z0-9_-]{3,32})/clip/([A-Za-z][A-Za-z0-9]{5,47})/?$` (`parseClipRoute()`, `src/live/clip/route.ts`, pure and tested). A match enters clip mode (see "Clip playback mode" below) instead of the normal viewer boot.

Otherwise: the username is the first path segment, lowercased and validated against `^[a-z0-9_-]{3,32}$` (invalid means a terminal "No channel" state). `GET /api/live/channel/<username>` supplies `title`, `category`, `categoryId`, `mediaBase`, and `emoteTwitchId`; a 404 is terminal. Chat starts regardless of playback. `?chat=popout` puts the page in popout mode: chat only, no player boot, no layout persistence.

Outside popout mode, boot also loads the chat column's ad spot: `loadAds("chat")` from `src/ads.ts` fetches once, and `renderAdSlot` renders into `#live-chat-feature`, which gets a `feature-filled` class toggled on whenever an ad rendered. This is the only ad slot the viewer (or any other page) renders.

`live.ts` is the entry (channel lookup, header fill-in, wiring). Its internals live in `src/live/`: `dom.ts` (element lookups), `constants.ts` (tuning constants), `icons.ts` (SVG strings), `format.ts` (`formatUptime`/`formatBehind`), `seekbar.ts`, `quality-menu.ts` (the WS quality ladder, the hls.js level list, and the low-latency upsell row), `quality-upsell.ts` (the locked-quality and low-latency subscription panels), `stream-info.ts` (viewer odometer, viewcount socket, uptime, fps), `layout.ts`, `fullscreen.ts`, `cinema.ts`, `browse-mini.ts`, `controls.ts`, `follow.ts`, `login-modal.ts`, and `clip/` (the clip button and clip playback mode, described below). The transport itself lives in `src/live/player/`: `context.ts` (the generation-guarded transport state), `lifecycle.ts` (teardown, restart, retry backoff), `ws.ts` (WS+MSE transport), `mse.ts` (SourceBuffer append/prune/quota), `quota.ts` (the pure quota-trim decision), `hls.ts` (the HLS transport, both native and hls.js, plus the presence beacon), `hls-support.ts` (pure capability probes: `mseSupported`/`canUseNativeHLS`/`canUseHlsJs`), `chase.ts`/`chase-decision.ts` (the latency chase), `health.ts` (the health timer), and `prewarm.ts`/`prewarm-ready.ts`/`adoption.ts`/`handover-decision.ts` (the raid seamless-handover prewarm, described under Raids below). Pieces shared with the embed player live in `src/player-shared/`: `viewer-claim.ts` (`parseViewerClaim`, decoding the captcha token's `q` field), `transport-choice.ts` (`chooseTransport`, the D11 selection logic), and `needs-credentials.ts` (the hls.js `xhrSetup` credentials predicate), alongside the pre-existing `viewer-id.ts`, `ws-url.ts`, and `transport-fallback.ts`.

### Transport selection

Boot awaits the viewer's captcha token (`getCaptchaToken()`, already pre-warmed earlier in boot) and decodes its `q` field with `parseViewerClaim()` (`src/player-shared/viewer-claim.ts`): `claim = q - (q % 2)`, `lowLatency = q` odd, defaulting to claim 0 / no low latency for a missing, legacy 3-part, or malformed token. `chooseTransport()` (`src/player-shared/transport-choice.ts`) then picks one of `"ws" | "hls-native" | "hls-js" | "unsupported"`:

- `ws` only when `MediaSource` is supported AND the token carries the low latency bit AND the WS transport has not already been denied this page load (`ctx.llDenied`, set on a `4428` close, see "WS+MSE path" below). WS is the paid `watch_ll` low-latency perk (~1 s).
- Otherwise HLS: native (`video.canPlayType("application/vnd.apple.mpegurl")`, in practice Safari) is preferred over `hls.js` (`Hls.isSupported()`) when both are available. HLS via the BunnyCDN-fronted origin is the default free path (hls.js ~2-4 s, Safari native ~3-5 s).
- Neither available: `"unsupported"`, a terminal "Playback not supported".

A `localStorage` key `transport` set to `ws` or `hls` overrides the automatic choice for debugging (an unrecognized value is ignored; `ws` still falls back to HLS when `MediaSource` is genuinely unsupported). A mid-stream MSE failure (`NotSupportedError`, unsupported codec string) re-runs the same native-then-hls.js preference via `fallbackFromMSE()`.

### Lifecycle

Player state is one of `offline`, `connecting`, `buffering`, `playing`, `reconnecting`, plus a terminal flag for unrecoverable cases. Every transport attempt bumps a generation counter; all async callbacks check `isCurrent(gen)` so a torn-down attempt cannot mutate the current one. Per-generation listeners are registered through `track()` and removed by `fullTeardown()`, which also closes the socket, drops the SourceBuffer, clears the append queue, and blanks the video element.

Retries use exponential backoff (1 s doubling to 15 s, reset on successful playback or on the first transition into offline). Before each retry the channel API is re-fetched (at most every 30 s) to pick up a changed `mediaBase`. A health timer (5 s, only while the tab is visible) restarts the transport when media stops arriving or playback stops progressing for 15 s while "playing", or when a non-playing state is stuck for 20 s. `visibilitychange`, `online`, and fullscreen settle also trigger a health check; `pagehide` tears down and `pageshow` (including back/forward cache restores) rebuilds.

### WS+MSE path

The socket URL is `<base as ws(s)>/ws/live?u=<username>&viewer_id=<id><captcha>`, where `base` is chosen by `chooseTransportBase(ctx.wssBase, ctx.mediaBase)` (`src/player-shared/transport-fallback.ts`, pure and tested): when the channel API returned a `wssBase` (go-live's optional direct TLS WebSocket listener, bypassing Apache) and that base has not already failed this page load, it is preferred over the `mediaBase`-derived, Apache-proxied URL. The captcha token query (`<captcha>`) is appended identically regardless of which base is used. The first text frame is JSON carrying `codecs` (used to build the `video/mp4; codecs="..."` SourceBuffer), plus optional `viewers`, `started` (drives the uptime readout), `width`/`height`/`fps` (seed the quality readout); receiving it is this transport's definition of "joined". Later text frames update the viewer count. Binary frames are fMP4 chunks pushed through an append queue into a single `segments`-mode SourceBuffer.

Close codes: `4404` means the channel is offline (retry loop with poster), `1000` means the stream ended (same), `4408` means the server dropped this viewer for falling behind (one immediate reconnect, then backoff), `4428` means the server denied the low-latency bit (the `watch_ll` perk lapsed or was never held under `LIVE_WS_PREMIUM`): the client sets `ctx.llDenied`, re-runs `chooseTransport()` (which now fails the WS branch) and restarts into whichever HLS path that yields, exactly as if the token had never carried the bit; anything else is a reconnect with backoff. A CONNECTION-level failure of a direct attempt - the socket closes or errors before the join frame ever arrives - is handled first, ahead of all of the above: `markDirectFailed(ctx.wssBase)` records the failure for the rest of the page load (a module-level `Set` keyed by base, so a different channel or region's `wssBase` is unaffected), and the very next attempt retries immediately through the `mediaBase`-derived URL without burning the normal exponential retry backoff (mirroring the existing quality-unavailable immediate-retry path). Once a direct base has failed it stays on the Apache-proxied path for the rest of the page load; a later disconnect after a successful direct join is treated as an ordinary reconnect (still through the direct base) rather than a failure.

A 500 ms chase timer manages latency: playback starts 0.8 s behind the live edge once enough is buffered; a gap over 1.3 s plays at 1.08x until it closes, a gap over 6 s snaps to the edge.

### DVR rewind (WS only)

The SourceBuffer keeps up to 300 s behind the playhead. Once at least 10 s is buffered, a seek bar appears with a draggable thumb, a "-m:ss" behind-live readout, and a LIVE / GO LIVE chip. Seeking more than 2 s behind the edge sets `behindLive`, which suspends the latency chase and edge snapping; a guard nudges the playhead forward if pruning approaches it. GO LIVE snaps back to the edge at rate 1. `QuotaExceededError` on append trims to the DVR horizon first and halves the kept window toward a 5 s floor only on repeated failures, restoring 300 s after a clean append. The DVR window is only what this client has received since connecting.

### Clip button (WS only)

Clip creation happens on its own page in a new tab; the viewer only exposes the entry point. A clip button appears in the controls once `transportKind` is `ws` and the live video's buffered range covers at least 10 s, next to the cinema and fullscreen buttons (`src/live/clip/button.ts`); it stays hidden on password-protected channels (`ctx.clipsDisabled`, set from the channel payload's `passwordRequired`), which refuse every clip path server-side. Its click handler calls `window.open("/clip/create?channel=<username>", "_blank")` synchronously, before any `await`, so the browser does not treat it as a blocked popup. Signed out (no valid `dash_token` in `sessionStorage`, `src/session-token.ts`), it opens the login modal with a `clip` intent instead; on successful login the modal (`src/live/login-modal.ts`) opens the same new tab. Live playback is never touched by any of this: there is no freeze machinery, no pin lifecycle, and no editor overlay in the viewer.

### Clip playback mode (`src/live/clip/`)

A path matching the clip route puts `live.ts` into clip mode (`bootClipMode()`, `src/live/clip/mode.ts`) instead of the normal viewer boot. The page is built to look identical to that channel's normal (offline) viewer page, with the clip standing in for the live video: the same info bar, channel rail, chat column, follow controls, and profile-panel-by-default behavior are wired up (`startChannelRail()`, `initFollow()`, `connectViewcount()`, `startChat()`, the chat ad slot, captcha anchoring, and `applyDefaultProfileVisibility(true)` all run exactly as they do for the normal viewer), all keyed off `ctx.username`/`ctx.displayUsername` (`src/live/player/context.ts`) set to the route's channel. `beginTransport()` is never called and `wirePageLifecycle()` is never wired, so no WS/HLS transport, health timer, or retry backoff is ever registered for this mode; `ctx.transportKind` stays at its default `"none"`.

It fetches `GET /api/live/clips/{code}` (`src/clip-status-poll.ts`, shared with the clip editor's post-create polling) and `GET /api/live/channel/{channel}` (for category, language, emote set, and the `live` flag) in parallel. A clip `channel` mismatch (case-insensitively), a 404, or an unparseable response renders a not-found state into the existing `#live-poster` element, reused as-is with the channel's profile banner behind it (mirroring the normal page's offline art) rather than through any transport-lifecycle helper. The clip's title populates the existing info bar (`#live-title-text`) alongside the channel's real category and language; `#live-name` shows the channel. A `status` of `processing` polls every 2 s (visibility-gated) showing the same `phase`/`queuePosition`-aware `clipProcessingMessage()` (`src/clip-processing-message.ts`) the editor uses.

`ready` sets the stage `video`'s `src` to the response's `url` and its `poster` to `thumbnailUrl` when present, and reveals the custom `.live-controls` row (`src/live/clip/player.ts`) instead of native controls: play/pause with the live player's icon set, a seek bar reusing the live seekbar's markup and CSS driven off `video.currentTime`/`duration` instead of the DVR buffered range, a current/total time readout (`#live-clip-time`, styled like `.live-quality`), volume, and fullscreen (via the shared `fullscreen.ts` module targeting the same stage element). Space toggles playback, the left/right arrows seek 5 s, and clicking the video toggles playback; the pure seek/format math lives in `src/live/clip/time.ts` (tested). Chat/layout chrome (chat toggle, side, popout, fullscreen, cinema mode, the touch-reveal controls fade) and the volume/fullscreen wiring are shared with the normal viewer via exported `wireChatAndLayoutChrome()`/`wireVolumeControl()`/`wireFullscreenControl()`/`wireKeyboardShortcuts()` helpers in `src/live/controls.ts`, so none of it duplicates the transport-coupled parts of `wireControls()` (DVR seek bar, quality menu, clip button, health-aware play handling, browse mode, page lifecycle).

When the channel chrome response indicates the channel is currently live, a prominent accent-colored "Watch live now" button (`#live-clip-watch-live`, styled unmissable, top-center of the stage) links to `/{channel}`, on top of the normal chrome rather than instead of it.

### Clip editor page (`src/clip-editor.ts`)

`/clip/create?channel=<name>`: a dedicated page opened in a new tab, entry `src/clip-editor.ts`, internals in `src/clip-editor/`, markup `public/clip-editor.html` with its CSS inline under one `.clip-editor-page` class.

Boot (`src/clip-editor/boot.ts`): the `channel` query parameter is validated against the same username shape the viewer uses (`parseChannelParam()`, `src/clip-editor/channel.ts`); invalid or missing is a terminal state. The session is then checked the way other site pages do: an existing valid `dash_token` is accepted as-is, otherwise `GET /api/auth/session` (credentials included) is tried once to pick up a session established elsewhere on the site; either way failing redirects to `/login?return=<this page's URL>` (`src/clip-editor/session.ts`).

Once signed in, it `POST`s `/api/main/v1/clips/pin?channel=<channel>` with the `Bearer` header and gets back `{pin, nowMs, windowMs}` (`src/clip-editor/pin-api.ts`). A `404` shows a clear "this channel cannot be clipped right now" state; a `403` means the channel is password protected and clips are disabled for it; a `429` shows a rate-limit message; a `401` redirects to login.

With a pin in hand, it previews the whole pinned window through `hls.js` (the repo's one sanctioned runtime dependency, reachable from three entries: this page, the channel viewer, and the embed player, see the README invariant and "Transport selection" above; reachable only from this page's own import graph here, so it bundles solely into `public/clip-editor.js`; every page outside those three stays dependency-free) playing an HLS VOD manifest instead of downloading the window itself. `src/clip-editor/media.ts` builds the playlist URL (`clipPlaylistUrl()`, `GET /api/main/v1/clips/pin/hls?channel=&pin=`), fetches it once directly (`fetchPinMediaHeaders()`) purely to read the `X-Now-Ms`/`X-Window-Ms`/`X-Media-Start-Ms` response headers into `state.nowMs`/`windowMs`/`mediaStartMs` (the backend doesn't expose them any other way), then hands the same URL to a fresh `Hls` instance (`createClipHls()`: `lowLatencyMode: false`, `backBufferLength: 60` so memory stays flat over a several-minute window, `xhrSetup` attaching the session `Bearer` token to every request hls.js makes, including every segment fetch). The editor becomes interactive as soon as `Hls.Events.MANIFEST_PARSED` fires (`src/clip-editor/boot.ts`): the whole window's duration and segment list are known from the manifest alone, so seeking or scrubbing anywhere is immediate, hls.js fetches whichever segment covers the target position on demand. A small overlay (spinner and label, `setBuffering()`) covers the video only while `hls.js` is still parsing the manifest and again whenever the native `waiting` event fires mid-playback (hls.js fetching a segment that hasn't landed yet); it is not a progress bar; there is nothing to sum since segments load out of order and on demand.

`video.currentTime` is not the pin's absolute media timeline: hls.js's fMP4 passthrough remuxer rebases every level so that the first fragment it ever remuxes becomes `currentTime = 0` (`node_modules/hls.js/src/remux/passthrough-remuxer.ts`, `startTime = decodeTime - initPTS.baseTime / initPTS.timescale` where `initPTS` is captured from that first fragment's own container timestamp). Since go-live's playlist always serves segment 0 as the pin's oldest fragment, and its `#EXTINF` durations are the exact real per-segment durations rather than independently declared ones, that rebase point is exactly `X-Media-Start-Ms` (`state.mediaStartMs`) with no drift for the rest of the window. The conversion is centralized in `src/clip-editor/media-timeline.ts` (`mediaMsFromCurrentTime()`/`currentTimeFromMediaMs()`, pure and tested) and used everywhere a `currentTime` needs to become an absolute media-timeline ms or back (`src/clip-editor/playhead.ts`'s `currentPlayheadMs()`/`seekTo()`, and `src/clip-editor/controls.ts`'s selection-playback stop condition); nothing else touches `videoEl.currentTime` directly.

Quota resilience rides on `backBufferLength` keeping steady-state memory low plus hls.js's own non-fatal handling of a `QuotaExceededError` during append (`Hls.ErrorDetails.BUFFER_FULL_ERROR`: hls.js stops appending further segments but does not tear anything down); the editor additionally surfaces a one-line notice (`setQuotaNotice()`, `#ce-quota-notice`) on that event and otherwise leaves playback, selection, and the pin alone. Other fatal hls.js errors get one recovery attempt (`hls.startLoad()` for a network error, `hls.recoverMediaError()` for a media error) before falling back to the same `media-error` state a browser with no MSE support gets from `Hls.isSupported()` returning false.

The UI is a video (click or Space to play/pause), a full-window overview strip (click/drag to seek) and a zoomable/pannable detail strip underneath, both DOM-built. On the detail strip, the mouse wheel zooms around the cursor and dragging pans once zoomed (`zoomWindow()`/`panWindow()`, `src/clip-editor/zoom.ts`, pure and tested); dragging the background when not zoomed seeks instead. Two draggable handles mark the in/out points, clamped between 3 s and 30 s apart within the loaded window (`clampSelection()`, `src/clip-editor/clamp.ts`, pure and tested); `I`/`O` keys and the "Set in"/"Set out" buttons set a handle to the current playhead, arrow keys step the playhead 1 s (5 s with Shift), and a "Play selection" button plays from the in point to the out point and pauses. A duration readout tracks the selection span.

While the editor stays open with a pin, `src/clip-editor/create.ts` renews it every 5 minutes via `POST /api/main/v1/clips/pin/renew?channel=&pin=`; a failed renewal ends the session. The pin is released with a best-effort `DELETE /api/main/v1/clips/pin?channel=&pin=` (`fetch` with `keepalive: true`) on `pagehide` unless a clip was already submitted, since the server consumes the pin as part of creation.

Submitting is a bodyless `POST /api/main/v1/clips?channel=&title=&pin=&startBehindMs=&endBehindMs=` with the `Bearer` header, where the behind values are `nowMs` minus the selection bounds in milliseconds (`behindMsFromSelection()`, `src/clip-editor/behind.ts`, pure and tested), computed on the same media timeline the loaded window uses. A `202`/`200` gives `{id}`, the new word-style clip code (for example `DarkMuffinScooter`). A `409`, `410`, or `422` is a failed clip; a `429` returns to the form with a rate-limit message and keeps the pin; a `503` ends the session as feature-unavailable. On success the editor polls `GET /api/live/clips/{id}` (`src/clip-status-poll.ts`, the same visibility-gated pattern as `src/explore/poll.ts`) showing queue position and encoding state via `clipProcessingMessage()`, then shows the final `/{channel}/clip/{code}` link with a copy button and a link to open it.

### HLS path (native and hls.js)

Both HLS variants (`hls-native` and `hls-js`) share `src/live/player/hls.ts`. The master playlist is always fetched directly from `mediaBase`, never through a CDN base, as `${mediaBase}/hls/<username>/master.m3u8?t=<captcha token>`; go-live's per-region BunnyCDN base (`hlsBase`, carried on the channel payload, `src/api.ts`, present only as a rollback signal) never reaches the player directly, since a configured CDN base only rewrites the variant URIs *inside* that master to absolute CDN URLs, which the player follows transparently. The master fetch is probed once (credentials included) before starting either path: a `403` with `{"error":"quality-locked"}` opens the locked-quality subscription upsell (`src/live/quality-upsell.ts`) instead of starting playback.

- **Native** (`hls-native`, Safari): `video.src` is set straight to the master URL; a cookie for a password-protected channel rides same-site automatically.
- **hls.js** (`hls-js`, every other browser without WS access): `new Hls({ lowLatencyMode: true, backBufferLength: 30, liveSyncDuration: 2.5, maxLiveSyncPlaybackRate: 1.08, enableWorker: true, xhrSetup })` attaches to the video element and loads the master. `xhrSetup` sets `xhr.withCredentials` only when the request URL's origin equals `mediaBase`'s origin (`needsCredentials()`, `src/player-shared/needs-credentials.ts`, pure and tested): the master fetch needs the `stream_pass_<channel>` cookie on private/ticketed streams, while CDN-served renditions must stay credential-free (their auth is the Bunny URL token, and a credentialed cross-origin request would fail CORS against a cached response). `Hls.Events.ERROR` fatal cases feed the existing `restartAfterFailure()`/`scheduleRestart()` retry lifecycle; `hls.destroy()` runs inside `fullTeardown()`. Non-fatal network errors rely on hls.js's own internal retries.

Both paths share the video element's `playing`/`ended` listeners (state transitions, retry-backoff reset, stream-end handling). Since HLS fetches otherwise never reveal a real viewer, a presence beacon posts `<mediaBase>/hls/<username>/beat?id=<viewer id>` every 10 s, unchanged; the viewer id is a random 16-hex value persisted in localStorage (`live_hid`) and also sent on the WS URL. The seek bar never shows on either HLS path.

**Quality menu and low-latency upsell**: for `hls-js`, the quality popup lists `hls.js`'s levels (label built from height and frame rate via the same `streamQualityText()` the locked-quality upsell uses) with a leading "Auto" entry; picking a level pins `hls.currentLevel`, picking Auto restores ABR (`hls.autoLevelEnabled`). Native Safari exposes no levels to switch. Both HLS variants add a trailing padlocked "Low latency" row to the popup while the stream is live, opening the subscription upsell panel with a line about the `watch_ll` perk (`openLowLatencyUpsell()`, reusing the same padlock rendering as a locked WS quality rung); WS viewers, who already have the perk, never see that row.

### Layout and modes

- **Layout**: `auto | horizontal | vertical`, cycled by a navbar button and persisted (`live-layout`); auto derives vertical from `(max-width: 900px) and (orientation: portrait)`. `syncLayout()` is the single function applying it, re-run on resize, orientation change, visual viewport resize, and after fullscreen exits settle (two rAFs plus a 120 ms timeout).
- **Chat column**: `fitChat()` sizes chat (300 to 560 px) so the video fills the remaining width at its real aspect ratio; collapsed state persists (`live-chat-collapsed`), side persists (`live-chat-side` toggles `body.chat-left`), and a chat fullscreen mode exists for mobile (native fullscreen when available, CSS lock otherwise).
- **Live channel rail**: polls `GET /api/live/explore` plus `GET /api/follows/mine` every 10 s while visible, splits channels into a Following section on top and remaining live channels below (each sorted by viewer count, ties alphabetical), highlights the current channel, and links directly to every live viewer page. Collapsed mode and narrow horizontal layouts shrink to a single avatar-wide column. Its collapsed state persists under `live-channel-rail-collapsed`; narrower horizontal layouts keep a compact avatar-and-name rail, while vertical, cinema, chat fullscreen, chat popout, fullscreen-video, and browse modes pause polling until the rail becomes visible again. The page-agnostic core (`src/channel-rail.ts`) also renders and polls on the explore page (`src/explore.ts`), highlighting no channel there; it is skipped entirely in framed mode, since the explore page is then embedded as the browse picture-in-picture iframe, which already has the viewer's own rail.
- **Cinema mode**: a pure CSS body class hiding navbar and info bar; hidden and auto-exited in vertical layout and popout; Escape exits; never touches the Fullscreen API.
- **Browse picture-in-picture**: clicking Browse or the brand while actively watching intercepts navigation. The page `pushState`s to `/`, shows a full-viewport iframe of `/?framed=1`, and CSS shrinks the same stage (same video element, same socket, no interruption) into a mini player. The mini player's close button parks the player (full teardown, offline state, no retry scheduling); returning to the channel un-parks it and resumes the normal reconnect lifecycle. `popstate` re-syncs the mode for back/forward.
- **Viewer count** renders as a per-digit odometer; **uptime** ticks from the join frame's `started`; **fps** is measured client-side from `getVideoPlaybackQuality()` deltas over media time.
- **Controls**: play/pause, mute, volume slider (hidden on iOS and anywhere volume writes do not stick, probed by `volumeIsSettable()`), fullscreen with WebKit fallbacks down to `video.webkitEnterFullscreen()`, keyboard shortcuts (Space, M, F) when no interactive element has focus, tap-to-reveal controls with a 3 s fade on touch, and tap-to-unmute on the stage.

There is no separate public clip page. A created clip plays at `/<channel>/clip/<code>`, served with the channel viewer's own `live.html` template (the backend splices clip `og`/`twitter` meta into it server-side for that route); see "Clip playback mode" above. The spliced meta differs by ready state and consumer: Discord (and other `og:video` unfurlers) always gets a playable inline embed straight off `og:video` once the clip is ready, while X (Twitter) ignores `og:video` for inline playback and instead needs a Twitter player card (`twitter:card=player`) pointing at an iframe-embeddable page, which is what `src/clip-embed.ts` (below) exists to serve; before the clip is ready both consumers fall back to a static `summary_large_image`/plain `og` card with no video meta at all.

## Chat client (`src/live-chat.ts`)

Started by the viewer via `startChat(username, emoteTwitchId)`. Speaks the IRC line protocol over a WebSocket to `/ws/irc` on the page origin, one or more `\r\n`-separated lines per text frame.

`live-chat.ts` is a facade exporting `startChat`/`stopChat`/`reconnectChatAfterLogin`; everything else lives in `src/chat/`: `dom.ts` (element lookups), `context.ts` (connection and identity state), `irc.ts` (line parsing), `text.ts` (truncation, escaping, mention matching), `members.ts` (roles, ranks, the NAMES prefix decoder), `badges.ts`, `render.ts` (message body token rendering), `messages.ts` (append/trim/reply bar/moderation actions), `pins.ts`, `panels.ts` (userlist and help/settings panels), `suggest.ts` (autocomplete), and `connection.ts` (connect/retry/dispatch). `chat-emotes.ts` stays at the top level and is used from `chat/`; the emote-picker autocomplete matching that used to live in a separate `chat-suggest.ts` is now part of `chat/suggest.ts`.

### Connection and identity

`connect()` (`src/chat/connection.ts`) resets member/role/pin state synchronously, then resolves the socket URL through `src/chat/ws-config.ts`'s `getChatWssBase()`: a plain `fetch("/api/live/ws-config")` made once per page load and cached (failure or a missing `chatWss` field just resolves to `""`, meaning no direct chat this attempt; a failure is retried on the next call rather than staying cached). The resulting base and the page-origin fallback go through the same `chooseTransportBase()` (`src/player-shared/transport-fallback.ts`) the video player uses: a configured, not-yet-failed `chatWss` connects directly to go-irc, bypassing Apache's `/ws/irc` proxy; otherwise (or once that base has failed once this page load) it connects to `/ws/irc` on the page origin as before. On open the client sends `CAP REQ :message-tags echo-message draft/message-redaction`, then `NICK`/`USER` with a guest nick bid (a stored `guest_<8hex>` value under `live-chat-guest-nick`, generated if absent; a legacy key is migrated once). The server is the sole nick authority: the confirmed nick is read back from `001`, persisted only if it matches the guest pattern, and then the client joins `#<username>` - `ctx.joined` flips true on that own-JOIN echo, which doubles as this transport's "joined" signal for fallback purposes. Signed-in state is checked separately via `GET /api/auth/session`; the session cookie also rides the WebSocket handshake, which is how an account gets its real name.

A CONNECTION-level failure of a direct `chatWss` attempt (close or error before the own-JOIN arrives) is handled ahead of every other close reason: `markDirectFailed()` records it for the rest of the page load and the very next reconnect fires almost immediately (100 ms) straight at the origin-derived URL, without spending one of the normal backoff steps below. Once failed, that base stays on the origin path for the rest of the page load.

Reconnects: 5 s normally, 30 s after a flood kill (close 4400) or while banned, and a "Chat is open in too many windows." message plus 30 s on close reason `session-limit`. Close codes 4400/4401/4402/1009 render explanatory system lines. A new connection resets all member/role/pin state.

### Composer states

`updateComposer()` picks one of: disabled input before the own-JOIN echo arrives; a full-width "Log in to chat" link (with `?return=`) when the user is a guest (not signed in, or carrying the guest `?` prefix); an enabled textarea placeholder "Chat as <nick>" otherwise; and a terminal banned state (474 or being KICKed) that hides everything, closes the socket, and only retries slowly. The composer is a textarea that auto-grows to 120 px; Enter sends, Shift+Enter inserts a newline.

### Members, roles, badges

`NAMES` (353) replies and JOIN/PART/QUIT/KICK/MODE maintain the member map. A name's leading prefix run encodes roles: `@` owner, `%` staff, `&` bot, `+` mod, `~` VIP, `*` subscriber, `=` unverified account, `?` guest. Badges stack in the order staff, owner (computed as name equals channel), bot, mod, VIP, subscriber, unverified, rendered from `public/static/img/badge-*.svg`. `MODE +v/-v` toggles mod, `+V/-V` toggles VIP. The subscriber badge is cosmetic only: it carries no rank and no moderation authority. The viewer list panel (cog button) replaces the chat body and buckets members Staff / Broadcaster / Bots / Moderators / VIPs / Users / Guests; a help panel (`?` button) shows a static command reference, and the two panels are mutually exclusive.

### Messages

- Incoming `PRIVMSG` to the channel renders nick (colored by a per-user `color` tag when present, else a name-hash HSL color), badges, and the body. A `PRIVMSG` to any other target renders as a whisper line (outgoing `↪ <to>` or incoming `<from> whispers`).
- The body renderer splits on whitespace and per token emits: a 7TV emote image, a `@mention` span, a safe link anchor (`http(s)` only via `new URL`, `rel="noopener noreferrer nofollow ugc"`, no referrer, trailing punctuation and unbalanced closing brackets split off), or plain text. Everything is DOM-built; no innerHTML for user content.
- **Zero-width emotes**: every rendered emote is wrapped in an inline stack; a zero-width emote (7TV flag bit 0 or data flag bit 8) following another emote is absolutely centered on top of that stack.
- **Echo and local echo**: with `echo-message` acked, the server's tagged copy renders (carrying `@msgid`); otherwise the client echoes locally, except for messages the server intercepts (whispers always, any dot-command when the sender has a mod role).
- **Replies**: hover actions include a reply button that sets a reply bar; sending prepends `@+reply=<msgid>`. Incoming replies render a clickable quote of the parent (looked up by `data-msgid`, scroll-and-flash on click); a reply to you or an `@you` mention highlights the line.
- **Channel point redemptions**: a custom-reward redemption arrives as an ordinary system line and needs no special handling; a highlight redemption arrives as a normal `PRIVMSG` carrying the `highlight=1` server tag (parsed in `src/chat/irc.ts`, tested) and renders with a distinct amber background (`live-chat-highlighted`). A signed-in viewer who is not the channel owner gets a redeem button in the composer actions (`src/chat/redeem-picker.ts`, the same popup pattern as the badge picker): the popup lists the channel's enabled rewards with costs (rows costing more than the points chip balance are disabled), a custom reward redeems immediately via `POST /points/{channel}/redeem` and updates the points chip from the returned balance, and the highlight reward arms the composer instead: a dismissible notice shows the pending cost with a cancel button, and the next submit routes the message text to the redeem endpoint instead of `PRIVMSG` (interception in `composer.ts`; the armed state helpers and request bodies live in the pure `src/chat/redeem-wire.ts`, tested). Redeem errors surface via the notices strip and keep the input; Escape closes the popup or disarms before the rest of the Escape chain.
- **Mention ping**: an incoming message from another user that mentions the signed-in nick (`shouldPingForMention`, `src/chat/mention-ping.ts`, pure and tested, reusing `textMentionsUsername` from `text.ts`) plays a short two-tone chirp synthesized with the Web Audio API (`src/chat/ping-sound.ts`, no audio assets, zero runtime dependencies). It never fires for the viewer's own messages, for a signed-out guest (no username to mention), or before the viewer's own JOIN has been confirmed. A pure throttle (`canPing`, `src/chat/ping-throttle.ts`, `PING_THROTTLE_MS = 3000`) caps it to one ping per 3 seconds regardless of mention volume. Autoplay policy means the `AudioContext` is only created and resumed lazily on the first click anywhere on the page or the first focus of the chat input (`primePingAudio()`); pings are silently skipped before that gesture. A "Mute pings" checkbox in the settings panel (`live-chat-mute-pings` in `localStorage`, disabled by default so pings play unless muted) gates it off entirely. This is wired only from `live-chat.ts`/`messages.ts`, so it never loads into the OBS chat overlay bundle, which has no user identity or settings panel to hang it off of.
- **Moderation**: with the redaction cap acked and a mod role, the message list gains hover delete (sends `.delete <msgid>`) and pin (sends `.pin <msgid>`) buttons; regular users get delete only on their own messages. An incoming `REDACT` rewrites the target line to a `<deleted message>` placeholder that keeps nick and badges but is no longer replyable. Messages tagged `automod=1` are shadow copies only mods receive; they render dimmed with a "blocked" chip, and are dropped entirely in popout mode.
- **Pins**: `PIN`/`UNPIN` lines maintain a multi-pin bar above the messages; each row jumps to the message on click; the close button unpins for everyone when the viewer is a mod, else dismisses locally.
- **Raids**: a `RAID #<channel> <target> <seconds>` line for the watched channel shows a banner on the player stage (`#live-raid-banner` in `live.html`, driven by `src/chat/raid.ts`) with the target, a live countdown, a "Join now" button and a "Stay here" button; staying dismisses locally and nothing else happens. `RAIDCANCEL #<channel>` removes the banner. Only on the WS+MSE transport does showing the banner start a seamless-handover prewarm; an HLS viewer (`hls-native` or `hls-js`) skips straight to the plain `location.assign` navigate fallback described below, since prewarm is gated to `ctx.transportKind === "ws"` both where a raid decides whether to start one (`canStartPrewarm()`, `src/live/player/handover-decision.ts`) and defensively inside `startPrewarm()` itself (`src/live/player/prewarm.ts`). On WS (`src/live/raid-handover.ts` registers itself into `raid.ts` via `setRaidHandover`, installed by `live.ts` outside popout mode; the session lives in `src/live/player/prewarm.ts`): a hidden muted `<video>` inside the stage (class `live-video-prewarm`, kept rendering at opacity 0) opens its own `/ws/live` connection to the target with `&prewarm=1`, the same `u`/`viewer_id` shape, and a freshly minted captcha token (`freshCaptchaQuery()` in `src/captcha.ts`, bypassing the token cache since the per-nonce use cap forbids reusing the player's token); go-live serves it the join meta, init segment and fragments but does not count it as a viewer until promoted, and kills unpromoted prewarms after 60 s with a 44xx close. The prewarm seeks just behind the live edge on its first buffered append (the fragment timeline is stream uptime, not zero) and counts readiness with the pure `src/live/player/prewarm-ready.ts` (tested): init appended, at least one media fragment appended, decodable buffered data, `readyState >= 2`. Join or countdown expiry then swaps in place instead of navigating: the promote text frame is sent on the prewarm socket, the old generation is torn down synchronously (old WebSocket closed, MediaSource detached, element blanked, so the viewer never consumes two streams beyond the swap moment), the prewarmed element replaces the visible one (taking over the `live-video` id, the user's volume/mute state, and re-attaching the element-bound control listeners via `attachVideoElementListeners`), and the page re-points itself at the target as if navigated minus the reload: `history.pushState` to `/<target>`, chat reconnects to the target's channel with a cleared feed, title/category/language chrome re-applies through the shared `src/live/channel-chrome.ts`, follow state re-initializes, and the viewcount socket re-watches. The new channel's transport ADOPTS the prewarm connection through the normal lifecycle: `ctx.adopt` (type in `src/live/player/adoption.ts`) is consumed by `beginTransport()`, which hands the already-open socket, MediaSource and SourceBuffer to `adoptWSTransport()` in `ws.ts` under a fresh generation instead of dialing its own, so health checks, chase, retries and later reconnects behave exactly as after a cold boot, and a further RAID on the swapped-to channel chains cleanly. Every imperfect case falls back to the v1 plain `location.assign` navigation, decided by the pure `src/live/player/handover-decision.ts` (tested): HLS transport, missing MediaSource, captcha mint failure, prewarm socket refused/closed/errored (including 4404 offline and the 44xx prewarm expiry), target locked, or not ready by Join/expiry; Stay here, RAIDCANCEL and leaving the page cancel the prewarm and close its socket immediately. On the target's side, `RAIDINCOMING #<channel> <raider> <viewers>` renders an accent-styled system line saying the raider is arriving with that many viewers. Wire parameters are validated by the pure `src/chat/raid-wire.ts` (tested): the target/raider must match the username shape and the countdown must be a positive integer, so a malformed line can never navigate the viewer anywhere. The banner lives inside `.live-left`, which popout chat hides, so popout windows only ever see the chat lines.
- The DOM keeps at most 200 messages and auto-scrolls only when already at the bottom.

### Emotes and autocomplete

7TV global emotes load from `https://7tv.io/v3/emote-sets/global`; when the channel API provided `emoteTwitchId`, the channel's borrowed set from `https://7tv.io/v3/users/twitch/<id>` is merged on top. An emote picker (grid with filter) inserts at the caret. Autocomplete triggers on `:prefix` (emotes), `@prefix` (members), or a bare first argument after `.ban .unban .timeout .mod .unmod .vip .unvip .whisper .w` (members without the `@`); Tab/arrows cycle, Enter accepts the highlighted entry or sends.

## Embed player (`src/embed.ts`)

A reduced viewer for `/embed/<username>`: same generation-guarded transport machinery as the main viewer (`chooseTransport()` off the captcha token's `q` bit, WS while entitled, native HLS or hls.js otherwise, a `4428` close setting `ctx.llDenied` and re-choosing into HLS exactly as the viewer does, channel API for `mediaBase`, viewer-id beacon on HLS, backoff retries, pagehide/pageshow handling) but no chat, no seek bar, no quality menu, no health timer, a 30 s buffer, and a simple offline poster. Autoplays muted; a click on the unmute button or anywhere on the stage unmutes.

`?preview=1` puts it in preview mode for the explorer's hover previews: the unmute button is suppressed and state transitions are reported to the parent window via `postMessage` with type `itzon:stream-preview` and state `connecting`, `playing`, or `unavailable`.

`?controls=1` gives the video element the native `controls` attribute, so an embedder gets the browser's own play/pause, volume and fullscreen UI without building their own (issue 71). Boot adds `embed-controls` to the body, sets the attribute, and suppresses the custom unmute button (`showUnmute()` treats the mode like preview, with a `body.embed-controls #embed-unmute { display: none }` backstop) since the native bar already carries mute and volume. `wireUnmute()` also skips the tap-anywhere-to-unmute gesture in this mode, so a click on the native control bar cannot unmute as a side effect of pausing. Nothing else changes: transport, poster, retries and preview reporting are untouched, and an embed without the param behaves exactly as before.

Mode precedence, resolved by the pure `src/embed/modes.ts` (tested in `tests/embed-modes.test.ts`) and re-exported by `context.ts`: `preview` wins over `controls` (hover previews must stay chromeless), and `controls` wins over `cleanfeed` (asking for controls is the more explicit request). `preview` and `cleanfeed` still compose.

`?cleanfeed=1` puts it in cleanfeed mode: video only, no chrome. Boot adds `embed-cleanfeed` to the body and `showUnmute()` treats the mode like preview, so the unmute button never appears (a `body.embed-cleanfeed #embed-unmute { display: none }` rule backstops it); boot also strips any `controls` attribute from the video element, and nothing in the embed ever sets one. The unmute button is the only UI chrome the embed renders, so cleanfeed hides exactly that; the offline/terminal poster text (`#embed-poster`, plain dim text on black) deliberately stays visible, since a silent black box on an offline channel reads as broken. Clicking the stage still unmutes (the existing tap-to-unmute gesture summons no UI and is the only audio path left), and preview's `postMessage` reporting is independent, so the two params compose.

`embed.ts` is the entry; its transport lives in `src/embed/`: `context.ts`, `dom.ts`, `constants.ts`, `lifecycle.ts`, `mse.ts`, `chase.ts`, and `transport.ts` (WS and both HLS variants: master-URL fetch, `hls.js` with the same `lowLatencyMode`/`backBufferLength`/`liveSyncDuration`/`maxLiveSyncPlaybackRate`/`enableWorker`/`xhrSetup` configuration as the viewer, and native `video.src`; no quality menu, since embeds have no UI chrome for one). Pieces that are genuinely identical to the viewer's player live in `src/player-shared/`: `viewer-id.ts` (the persisted HLS viewer id), `ws-url.ts` (media WS URL building), `transport-fallback.ts` (direct-`wssBase`-preferred, once-per-base-failure fallback to the `mediaBase`-derived URL, described in "WS+MSE path" above), `viewer-claim.ts` (captcha token `q` decode), `transport-choice.ts` (the D11 selection logic), and `needs-credentials.ts` (the hls.js `xhrSetup` credentials predicate); both `src/live/player/` and `src/embed/` import from there, so the embed player's transport selection and WS direct-base preference behave identically to the main viewer. The two transports are otherwise independent implementations, not a shared engine.

## Clip embed page (`src/clip-embed.ts`)

Serves `/embed/clip/<channel>/<code>`, the iframe-embeddable page a ready clip's `twitter:player` meta tag points at (`ClipHandler.buildClipMeta`, `java-backend`). X (Twitter) only ever plays video inline through a Twitter player card, which requires an HTTPS page it can frame, never a bare `.mp4`; this page is that target. It deliberately lives under the `/embed/` path prefix so it inherits the existing Apache anti-framing exclusion for `/embed/` and `/chat/` (`installation/apache.md` section 9a) with no header changes needed on the Apache side.

The route is parsed client-side and purely (`src/clip-embed/route.ts`, `parseClipEmbedRoute`, tested in `tests/clip-embed-route.test.ts`): channel `^[a-z0-9_-]{3,32}$`, code `^[A-Za-z][A-Za-z0-9]{5,47}$`, same shapes the main clip route (`src/live/clip/route.ts`) and the backend (`ClipCodes`/`AuthHandler.isValidUsername`) already enforce. An unparseable path renders the not-found state immediately with no network call.

On a valid route it does a single plain `fetch("/api/live/clips/<code>")` (`src/clip-status-poll.ts` is not reused here; this page has no polling, no processing/queue UI, and no dependency on the channel-chrome fetch the full clip mode makes) and checks the response's `channel` case-insensitively against the URL's channel segment; a fetch failure, a non-OK response, a channel mismatch, or a clip that isn't `status: "ready"` with a `url` all render the same small not-found state (`#clip-embed-state`) instead of the player. A matching, ready clip sets the video's `poster` to `thumbnailUrl` and `src` to `url`, then attempts a muted autoplay (X requires embedded video to start muted without a user gesture); native `controls` (not the site's custom clip controls) stay on the element throughout so a viewer can unmute or scrub without any script wiring of its own.

There is no chat, navbar, site nav, or analytics on this page, and no runtime dependency: markup is the static skeleton in `clip-embed.html` (video element, a state div, a corner link) plus `textContent`/attribute writes from `src/clip-embed.ts`, styled inline in the HTML file the same self-contained way `embed.html` is. The stage and video are both `position: absolute; inset: 0` sized to `100%`/`100%` with `object-fit: contain`, so the player fills whatever box the embedding page gives the iframe (X's player cards are roughly 16:9) at any size. A small accent-green corner link (`#clip-embed-open`, `target="_blank" rel="noopener"`) opens the real `/<channel>/clip/<code>` page in a new tab once the route parses, regardless of whether the clip itself loaded, so a viewer inside the X card can always reach the full site.

## OBS chat overlay (`src/chat-overlay.ts`)

`/chat/<username>` renders a transparent, read-only chat for use as an OBS browser source. It connects to `/ws/irc` as a fresh random guest, requests only `message-tags draft/message-redaction`, joins the channel, and renders `PRIVMSG` lines with the same badge and zero-width-emote logic as the main client. It sends nothing but the registration handshake, `PONG`, `JOIN`, and `NAMES`; NOTICEs are never rendered; a `REDACT` removes the line entirely (unlike the viewer's placeholder). Reconnects every 5 s, or 30 s after a 474/KICK. `SYSMSG` lines (raids, channel point redemptions) render as a distinct accented line, plain text with no nick or badges, only when `system=1` is set.

`src/chat-overlay/connection.ts` is its own standalone connect implementation (it does not import `src/chat/connection.ts`) and, unlike the main chat client, makes no API calls of its own before opening its socket. It deliberately keeps connecting to `/ws/irc` on the page origin only and does not fetch `/api/live/ws-config` or prefer a direct `chatWss`: the OBS browser source is meant to stay as simple as possible, and adding its first-ever API round trip purely to chase the direct-chat optimization was judged not worth it. If this module is ever merged into the shared one, it should pick up the same preference and fallback for free.

URL parameters:

| Param | Effect |
|---|---|
| `size=s\|l` | Smaller or larger text (default medium) |
| `fade=N` | Fade each message out after N seconds |
| `badges=0` | Hide badges |
| `emotes=0` | Disable emote rendering (skips the 7TV fetch) |
| `system=1` | Render `SYSMSG` lines (raids, channel point redemptions) |
| `bg=1` | Dark background panel instead of transparency |
| `shadow=0` | Disable text shadow |
| `align=right` | Right-align messages |
| `demo=1` | No connection; loops a scripted set of sample messages (used by the dashboard's overlay preview) |

`chat-overlay.ts` is the entry (URL params, boot). ## Guides and docs (`content/`, `scripts/build-content.ts`, `src/content-page.ts`)

`/guides` and `/docs` are two sections of generated static pages that replaced the single hash-routed `/wiki` on 2026-08-17. `/wiki` 301s to `/docs`; `wiki.html` and `src/wiki.ts` are gone.

The split exists for two reasons. The content had two audiences wedged into one page (three developer references, two creator guides, all titled "API documentation"), and hash fragments are not separate URLs, so `#chat`, `#obs` and `#oauth` were one indexable document competing for five unrelated queries with one title and one description.

- **Source**: `content/<section>/<slug>.html` holds the body of one page and nothing else, no `<h1>` and no head markup. `content/pages.ts` is the typed manifest: per section an id, heading, `<title>`, description, intro and kebab label; per page a section, slug, heading, `<title>`, description and index-card summary. Adding a page is one fragment plus one manifest entry.
- **Generation**: `scripts/build-content.ts` runs after `build:pages` (it resolves the hashed `content-page-<hash>.js` itself via the shared `scripts/built-name.ts`) and writes `public/<section>/<slug>.html` plus `public/<section>/index.html`, each a complete standalone document: canonical, description, Open Graph, Twitter card, breadcrumb, sidebar of sibling pages with the current one marked `aria-current`, and a cross-link to the other section. It also emits `public/sitemap-content.xml`, which the tracked `sitemap.xml` index references. All of it is gitignored build output.
- **Structured data**: every page carries `TechArticle` plus `BreadcrumbList`; the index pages carry `CollectionPage` plus `BreadcrumbList`. Deliberately not `HowTo`: Google removed HowTo rich results in 2023, so it would be markup that buys nothing. The ranking win here is the URL split, the per-page titles and descriptions, and the internal linking, not the schema.
- **Runtime**: `src/content-page.ts` is one shared bundle for every generated page. It boots the navbar, fills every `[data-fill=host]` span with `location.host` so hostnames are right on any deployment, and probes each `.content-guide` video with a `HEAD` fetch, removing the container when the file is absent (a media `error` event also removes it). So the OBS guide ships with no videos and the owner can drop mp4 files into `public/static/guides/` later with zero code changes.
- **Developer affordances**, all generic so every page gets them without touching content: each `<h2>` is given a slugified `id` and a hover-revealed `#` anchor at build time (`anchorHeadings`, pure and tested, with collision suffixes), a sidebar table of contents is emitted for any page with three or more headings and highlights the current section on scroll, and every `<pre>` gets a hover-revealed copy button wired through the shared `src/clipboard.ts`.
- **Styling**: `public/static/css/content.css`, carried over from the old inline wiki styles, minus the tab-switching rules that a standalone page does not need.
- **`shared.css` styles bare `nav` elements** (`background`, `border-bottom`, `display: flex`, `height: 48px`, `position: sticky`, `top: 0`, `z-index: 100`, `overflow: hidden`). Any `<nav>` outside the site header therefore needs an explicit reset, which `content.css` does for `.content-nav`, `.content-breadcrumb` and `.content-toc`. Without it the symptoms are a grey sticky bar behind the element, that bar floating over the site header while scrolling (`z-index: 100` beats the header's `50`), and every list item after the first being clipped away by the fixed height. The old `wiki.html` carried the same reset for `#wiki-topics`; that is what it was for.

Current pages: **Guides** are `obs-setup` (ingest URL and stream key from the Stream tab, OBS service/encoder walkthrough with the declared bitrate cap, keyframe interval, resolution and fps baselines, go-live checklist, common failures), `private-streams` (what closing a channel changes, and how the password gate behaves) and `badges` (every cosmetic and role badge at 96, 32 and 17 pixels with a sample chat line, and how each one is bought, earned automatically or given by staff; the automatic ones are Ambassador, Recruiter, Every Day, Full Orbit, Medal, Twenty-Four and Lucky). **Docs** are `api` (Bearer auth, the per-token rate limit and `X-RateLimit-Remaining`, every `/api/public/v1` endpoint with params, curl, example response and errors, the cursor pagination contract, and the token-free live status badge endpoints), `chat-bots` (IRC and WebSocket endpoints, token auth, IRCv3 tags, moderation commands, limits and close codes) and `oauth` (client registration, authorize URL, consent redirect, code-for-token exchange, userinfo, error codes, 60 s single-use codes and 1 h tokens).

## Pricing page (`src/pricing.ts`)

`/pricing` (Apache rewrite to `pricing.html`; `pricing` is reserved as a username) is the public, sessionless view of everything that can be bought. It exists because `GET /api/billing/tiers` requires a user session, so before it there was no way to see prices without registering first.

- **Static content is the SEO payload.** The heading, the lede, the "Free on every account" grid and the five-question FAQ are plain markup in `pricing.html`, so the page carries indexable copy with no JavaScript at all. `pricing.html` also embeds a static `FAQPage` JSON-LD block matching that FAQ verbatim.
- **Prices are hydrated.** `GET /api/live/billing/catalog` (unauthenticated, cached 5 minutes by the backend, region-aware for add-ons) returns tiers, add-ons, pass availability and the founder seat count with no user state and no Stripe price ids. The page renders tier cards, add-on cards and the founder card from it; the add-on and founder sections stay `hidden` when the catalog has nothing to show. A failed fetch replaces the tier grid with a retry message and leaves everything static intact.
- **CTAs branch on session.** `boot()` does one `GET /api/auth/session` and passes the result into `initSiteNav` as `knownSession`, so the navbar does not repeat the request. Signed in, every button links to `/dashboard/subscription`; signed out, to `/register?return=%2Fdashboard%2Fsubscription` (`subscriptionCtaHref`, `src/pricing/view.ts`, pure and tested). Nothing on this page ever calls checkout directly, so no payment path is reachable without a session.
- **DOM construction, not `innerHTML`.** Every card is built with `document.createElement` and `textContent`, so a config-supplied tier label or add-on note can never inject markup.
- **After the catalog renders** a `Service` + `Offer` JSON-LD block is appended to `<head>`, one offer per tier whose configured price parses as a number (a non-numeric price string is skipped rather than emitted as a broken offer).

Shared with the dashboard Subscription tab: `src/billing/catalog.ts` holds the catalog presentation rules both pages need (`amountText` currency formatting, `perkTokens`/`perkLines`/`perkLabel` perk naming, and `perkDelta`, the "Everything in X, plus:" rule that hides a tier's inherited perks when the tier below is fully covered, including `badge_*` covering `badge` and `watch_4k` covering `watch_2k`). `src/dash/tabs/subscription.ts` imports the same functions rather than keeping its own copies.

## Status page (`src/status.ts`)

`status.html` on the `status.<domain>` vhost (Apache rewrites `/` to it and proxies `/api/status/` to the status backend). Standalone: no session, no navbar, no cookies, inline CSS in the HTML file using the house palette. It fetches `GET /api/status/overview` relative to the page origin and renders the overall banner (operational green, degraded yellow, down red, anything else gray) plus one card per group with per-service rows: label, region tag when present, latency, 24 h and 90 day uptime percentages (`null` renders as "no data"), the last status change as relative time, and a status chip. Auto-refreshes every 30 s with a last-updated stamp; the interval skips ticks while `document.visibilityState` is hidden and a `visibilitychange` back to visible refreshes immediately when the data is stale. A failed or malformed fetch shows a "Status unavailable" banner and keeps the last rendered cards (or an explanatory line when nothing loaded yet). The pure pieces (payload parsing/normalization, uptime/latency formatting, relative time, banner mapping) live in `src/status/overview.ts`, tested in `tests/status-overview.test.ts`.

Under each service row sits a 90 day uptime strip: one bar per UTC day, green at 99.5% or better, amber down to 97%, red below that, and gray for a day with no samples at all, each with a `title` tooltip carrying the day, the percentage and the minutes down. The strip comes from `GET /api/status/history?days=90`, which also feeds a "Recent incidents" card below the group cards (the newest 20, newest first: service label, resolved or ongoing chip, local start time, duration, and the operator note when one is set) and a one-line note saying how much history actually exists (from `firstSampleAt`). History refreshes every 5 minutes while the live overview keeps its own 30 s cadence; both are visibility-gated the same way and each renders from whatever it last got, so a failing history fetch never blanks the live status and vice versa. Incident notes are written with `textContent` like every other value on the page, which is where the server-stored raw note gets sanitized. The pure pieces (payload parsing, bar level thresholds, UTC day keys, strip building with gaps, tooltip text, duration formatting, note trimming/capping, the history summary line) live in `src/status/history.ts`, tested in `tests/status-history.test.ts`.

## Sitewide degraded banner (`src/status-banner.ts`)

Every page that calls `initSiteNav` also starts `initStatusBanner()`: a 60 s visibility-gated poll of the same-origin `GET /api/status/banner` (the live vhost proxies `/api/status/` to the status backend). Three outcomes drive a pure state machine (`nextBannerState`, tested in `tests/status-banner.test.ts`): a healthy answer hides the banner and resets the error count; `degraded: true` shows a fixed bottom-left dismissible bar "Degraded performance: <friendly service labels>." with a link to `https://status.<host>`; three consecutive HTTP-5xx answers (Apache reachable, status backend not, meaning the monitoring itself is down) escalate to a generic "We're having technical difficulties" banner. Network-level fetch failures and 4xx change nothing at all, so a viewer's own flaky connection or an adblocker can never conjure an outage banner. Dismissing stores the banner's mode+services signature in sessionStorage and only that exact combination stays hidden; a change in affected services resurfaces it. The server decides which checks are viewer-relevant and how they are named, the client renders labels verbatim.

## Auth pages

All four call `initSiteNav(null)` and talk to `API_BASE` directly.

- **Login** (`src/user-login.ts`): boots hidden; an existing valid `dash_token` or a cookie session (`GET /api/auth/session`, accepted only for `kind === "user"`) redirects immediately to the `?return=` target (validated same-origin http(s), no embedded credentials) or `/dashboard`. `POST /api/auth/login` with `{username, password}`; a 429 with `retryAfter` starts a visible lockout countdown; success stores `dash_token`/`dash_kind` and redirects. A forgot-password section posts `{email}` to `/api/auth/forgot-password` and always shows a neutral confirmation.
- **Register** (`src/register.ts`): same already-signed-in redirect logic. Submission runs an invisible hCaptcha (`hcaptcha.execute`, 20 s watchdog, reset on error/expiry); the resulting token is sent with `{username, password, email, captchaToken}` to `POST /api/auth/register`; success stores the token and redirects like login.
- **Verify** (`src/verify.ts`): reads `?token=`, calls `GET /api/auth/verify?token=`, and on `{ok}` logs out any stored session, then links and auto-redirects (2.5 s) to the sign-in page matching the returned account `kind` on the corresponding host.
- **Reset password** (`src/reset-password.ts`): reads `?token=`, validates the two password fields match, posts `{token, newPassword}` to `POST /api/auth/reset-password`, and on success shows a done section and redirects to `/login`.

## OAuth consent page (`src/oauth-authorize.ts`)

`/oauth/authorize` (Apache rewrite to `oauth-authorize.html`; `oauth` is reserved as a username) is the "Sign in with itzon" consent page a third-party app sends its users to with `?client_id=&redirect_uri=&response_type=code&scope=identity&state=`. The query is parsed and validated purely client-side first (`parseAuthorizeParams()`, `src/oauth-authorize/params.ts`, tested: 32-hex client id, absolute http(s) fragment-free redirect URI, `response_type` exactly `code`, scope normalized by `normalizeScope()` mirroring the backend rules (valid set `identity`/`api:read`/`api:write`, space-separated, deduped, `identity` always implied, canonical order; anything else invalid, empty defaults to `identity`), state capped at 512 chars); an unparseable request renders a terminal error with no network call and never redirects anywhere.

The session boots the way the clip editor does (`src/oauth-authorize/session.ts`: stored `dash_token`, else one `GET /api/auth/session` cookie bootstrap); signed out redirects to `/login?return=<this page's URL>` and lands back here after login. It then calls `GET /oauth/authorize` (under `API_BASE`, Bearer) which validates the client and exact redirect match server-side and returns `{app, scope, username, pendingId}` (the `pendingId` is an opaque handle over the scope, client and redirect the SERVER validated); a 401 clears the stored token and round-trips through login, any other failure is terminal (again, no redirect, since the redirect URI was never validated). Success renders "APPNAME wants to verify your itzon identity" (or "wants to access your itzon account" when api scopes are requested) with one human-readable line per granted scope from `SCOPE_DESCRIPTIONS` (identity: confirm who you are; api:read: read your channel, followers and profile basics; api:write: update your stream title, category and language) rendered into `#oauth-scopes`, and Approve/Deny buttons. Approve posts `{pendingId}` and nothing else to `POST /oauth/consent` (Bearer), so the approved scope is exactly the one the card displayed and a client-supplied scope can never widen it (`consentRequest`/`displayedScope` are pure and tested) and navigates to the returned `{redirect}` (the registered redirect URI carrying `code` + `state`); Deny navigates to `buildDenyRedirect()` (`redirect_uri?error=access_denied&state=`, pure and tested) - safe to do client-side because the server already confirmed the redirect URI is registered.

## Dashboard

### Shell (`src/dashboard.ts`)

Boot sequence:

1. `initSiteNav("dashboard")`.
2. Session: use the stored `dash_token`, else `bootstrapSessionFromCookie()`; then `GET /api/auth/me` with the Bearer token (one cookie-bootstrap retry on failure); any dead end redirects to `/login`.
3. `me` provides `kind`, `username`, `flags`, `emailVerified`, and `tabs` (`[{id, label, pane, group?}]`), the sole source of which tabs exist. Boot also checks the session kind against the current hostname and redirects to the matching host when they disagree, preserving the requested tab; only `user` sessions are served by this dashboard.
4. Granted tabs are filtered to those with an entry in `TAB_LOADERS` (`stream`, `automation`, `channelpoints`, `stream-manager`, `chatbox`, `alertbox`, `multichat`, `stream-health`, `stream-summary`, `activity`, `settings`, `integration`, `channel-profile`, `clips`, `subscription`, `achievements`). Granted tabs without a local loader are not rendered as tabs; their presence makes the sidebar (and the mobile hamburger) show a single external link instead.
5. The sidebar is built with group headers (shown only when two or more distinct groups exist) plus a mobile toggle; `setBurgerExtra` injects the tab list into the shared navbar hamburger, as a one-open-at-a-time accordion when grouped.

Routing: the tab comes from `/dashboard/<tab>` (with `/dashboard.html/<tab>` and a legacy `#tab` hash fallback). `activateTab` fetches `/panes/<pane>.html` and dynamic-imports the tab module in parallel on first activation, inserts the pane, calls `init(pane)` once, then on every activation toggles pane visibility, calls the previous tab's `deactivate?()` and the new tab's `activate()`, and `pushState`s the URL. An activation sequence counter discards stale async completions; a failed load alerts and leaves the current tab. `popstate` re-activates from the URL; unknown or ungranted tabs normalize to the first granted tab via `replaceState`. Elements with `data-switch-tab` anywhere in the document switch tabs on click.

Tab modules export `init(pane)`, `activate()`, and optionally `deactivate()` (`TabModule` in `dash/session.ts`). Panes live in `public/panes/<pane>.html` and contain only markup; all behavior is in the module.

## SEO surface

Added 2026-08-17. Split across this repo and the backend, because a channel page's markup is produced by the backend renderer, not by this build.

**Static files in `public/`** (served straight off the docroot, no Apache route needed since none of them collide with the single-segment username catch-all):

- `robots.txt`: disallows the machine and overlay surfaces (`/api/`, `/ws/`, `/hls/`, `/thumb/`, `/clips/`, `/desktop/`, `/embed/`, `/chat/`, `/alerts/`, `/oauth/`, `/clip/create`, `/dashboard`, `/details`, `/multichat`, `/verify`, `/reset-password`) and points at `sitemap.xml`. `/login` is deliberately NOT in that list: it carries `<meta name="robots" content="noindex,follow">` instead, which only works if the crawler is allowed to fetch and read it. `/verify` and `/reset-password` are disallowed AND `noindex`, because their URLs carry a single-use token that a crawler fetching the page would consume.
- `sitemap.xml`: a sitemap index, referencing `sitemap-static.xml` (tracked), `sitemap-content.xml` (generated) and `sitemap-channels.xml` (the backend route, proxied by Apache).
- `sitemap-static.xml`: `/`, `/categories`, `/pricing`, `/register`, `/terms`, `/privacy`.
- `sitemap-content.xml`: generated, every `/guides` and `/docs` page (see the guides and docs section).
- `site.webmanifest`: name, icons, theme colour.

**Per-page head**: every page with a navbar carries a canonical, a description, Open Graph and Twitter card tags, `theme-color`, an apple-touch-icon and a `<title>` in `<Page> | ITZON` form. Overlay, embed, dashboard and auth pages carry `noindex`. `terms.html` and `privacy.html` are indexable on purpose (trust signals for a site taking payments); `impressum.html` stays `noindex,follow`.

**`<!--LIVE_TITLE-->`** in `live.html` is the second backend splice token beside the pre-existing `<!--LIVE_META-->`. It replaced the static `<title>Live</title>`, so the channel and clip page renderers (`LiveHandler.page`, `ClipHandler.clipPage`) emit the real per-channel title server-side instead of leaving `Live` in the markup until JavaScript runs. A backend that predates the token simply leaves the comment in the head. Client-side, `src/live/page-title.ts` produces the same strings (`channelPageTitle`, `clipPageTitle`, `chatPopoutTitle`, pure and tested) so the title the renderer writes and the title `live.ts` sets after the channel payload arrives agree instead of the client overwriting a good title with a bare username.

**Structured data**: the homepage carries a static `Organization` + `WebSite` graph; `/pricing` carries a static `FAQPage` plus a `Service`/`Offer` block appended once the catalog loads. The `VideoObject` + `BroadcastEvent` markup that earns a live badge in search results is emitted by the backend into `<!--LIVE_META-->`, only while a channel is actually live, and a `VideoObject` for a ready clip on a clip page.

**Performance**: `inter-latin.woff2` is preloaded on the two pages that matter for Largest Contentful Paint (explore and the channel viewer). Compression and cache headers are Apache's job and live in that runbook, not here; the content-hashed bundle names this build produces are what make a year-long immutable cache safe.
